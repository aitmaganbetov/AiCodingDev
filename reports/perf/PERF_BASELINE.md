# Базовый замер производительности и предложение SLO (P9-04, NFR-PERF-01)

Дата замера: 2026-11-08. Код: `main@51ab125` + рабочие изменения Phase 9 (до коммита). Сырые результаты
последнего прогона — [`results.json`](results.json). ТЗ §23: «измеренные SLO устанавливаются после базового
нагрузочного тестирования; не заявлять неподтверждённых цифр» — ниже только измеренные значения, SLO —
**предложение** для утверждения владельцем.

## 1. Методика

Скрипт [`scripts/perf/baseline.py`](../../scripts/perf/baseline.py) поднимает одноразовый стенд и удаляет его
после прогона; генератор нагрузки — [`scripts/perf/loadgen.py`](../../scripts/perf/loadgen.py) (asyncio + httpx,
без новых зависимостей; locust не используется).

* **Стенд:** отдельная БД на PostgreSQL 17 (роли и миграции до head — как у тестов, `tests/support/db.py`),
  частный `redis-server` без persistence, API — один процесс uvicorn (`aicd_api.main:create_app --factory`),
  воркеры `aicd-worker outbox` и `aicd-worker index` — настоящие процессы приложения с настройками по
  умолчанию (`outbox_batch_size=100`, `outbox_poll_seconds=0.5`). Генератор нагрузки — на том же хосте.
  Лимиты частоты API подняты (иначе измеряется rate limiter); аутентификация — настоящая (cookie-сессия + CSRF).
* **Модель нагрузки:** закрытый цикл: N виртуальных клиентов, следующий запрос — сразу после ответа;
  2 с прогрева не входят в статистику, затем 20 с измерения. Латентность — от отправки до полного чтения
  тела (`perf_counter`); перцентили nearest-rank по всем значениям, без выборки. Ошибка — HTTP ≥ 400 или
  сбой соединения.
* **Сценарии:**
  1. `run_create_c{1,8}` — `POST /api/v1/runs` с уникальным Idempotency-Key (команда + `run.created` в outbox
     одной транзакцией);
  2. `api_reads_c{1,16,64}` — по кругу: список run проекта (`limit=50`), run, задачи run, список проектов;
     данные — ~1,8–2,3 тыс. run, созданных сценарием 1;
  3. `outbox_throughput` — 5000 событий `run.state_changed` (20 run) одной транзакцией → время до публикации
     последнего воркером outbox (проекция в `run_event_log` + публикация в Dramatiq/Redis + сигнал SSE);
  4. `sse_fanout_{50,90}` — N разных пользователей (лимит 5 потоков на пользователя) подписаны на
     `GET /runs/{id}/events` одного run; генератор пишет 50 событий в outbox (10/с, по одному на транзакцию,
     как оркестратор); задержка = момент получения клиентом − `occurred_at` события (часы одного хоста);
  5. `indexing_medium_repo` — attach копии репозитория AiCodingDev (HEAD, 952 файла в git) → задание
     индексации → воркер `index`; время `started_at → finished_at` задания и ожидание в очереди.
* **Воспроизведение:**
  ```bash
  export AICD_PERF_DATABASE_ADMIN_URL=postgresql://<superuser>:<pw>@127.0.0.1:55432/postgres  # или AICD_TEST_DATABASE_ADMIN_URL
  uv run python -m scripts.perf.baseline --sse-clients 50 90 --out reports/perf/results.json
  # параметры: --duration, --read-concurrency, --create-concurrency, --sse-clients, --sse-events,
  #            --sse-rate, --outbox-events, --skip-indexing
  ```

|---|---|---|

## 5. Найденные ограничения

1. **Потолок ~100 SSE-потоков на процесс API.** Каждый поток держит соединение pub/sub из общего пула
   `redis.asyncio` (пул по умолчанию ограничен ~100 соединениями), а `max_streams_per_process = 1000`
   (`apps/api/aicd_api/routers/events.py`). Поток сверх пула получает **HTTP 500** (не 503/429).
   Рекомендация: задать `max_connections` пула Redis API ≥ `max_streams_per_process` + запас на rate limiter
   и сессии, либо снизить `max_streams_per_process` до размера пула и отвечать 503 `service_unavailable`.
   Не исправлено в P9-04 (за пределами задачи замера; требует решения по конфигурации) — открыть задачу.
2. **Outbox ~146 событий/с на один процесс диспетчера** (по событию: savepoint + `UPDATE runs` seq +
   INSERT `run_event_log` + публикация в Redis + UPDATE). Для всплесков (CLI-вывод многих задач) этого может
   не хватить; горизонтально масштабируется несколькими диспетчерами (`FOR UPDATE SKIP LOCKED` + блокировка
   run, `test_concurrent_dispatchers_keep_per_run_seq_monotonic`), замер с 2+ диспетчерами — §6.
3. **Один процесс API насыщается на ~90–120 rps** смешанных чтений на этом стенде; масштабирование —
   несколько процессов uvicorn/реплик (состояние сессий в PostgreSQL, rate limit/SSE — в Redis).

## 6. Предложение SLO (для утверждения владельцем; окно — 30 дней, профиль single-host)

| SLI | Предлагаемый SLO | Основание (замер) | Как измерять |
|---|---|---|---|
| Доступность API: доля ответов не-5xx | ≥ 99,5 % | 0 % 5xx в нагрузке до c64 | `aicd_http_requests_total{status=~"5.."}` |
| Латентность чтений API (GET), p95 | ≤ 500 мс при ≤ 16 одновременных клиентах на процесс | 256–264 мс p95 при c16 на нагруженном общем хосте; 26–30 мс при c1 | гистограмма длительности HTTP по маршрутам |
| Латентность создания run (`POST /runs`), p95 | ≤ 500 мс | 206–219 мс p95 при c8 | то же |
| Доставка событий run в SSE, p95 от commit | ≤ 2 с (≤ 100 потоков на процесс API) | 733–851 мс p95 (50–90 клиентов), 100 % доставка | `aicd_outbox_lag_seconds` + задержка SSE (метрика потока — предложить) |
| Публикация outbox: возраст старейшего неопубликованного | ≤ 60 с в 99 % минут; алерт > 300 с — как есть | 146–149 событий/с на диспетчер | `aicd_outbox_oldest_pending_age_seconds` |
| Индексация «среднего» репозитория (~1 тыс. файлов) от постановки до READY, p95 | ≤ 60 с | 3,9 с + 1,0 с в очереди | `indexing_jobs.finished_at − created_at`, `aicd_indexing_jobs_total` |

Перед утверждением: (а) повторить замер на выделенном стенде целевой конфигурации (отдельные хосты для БД и
генератора, без посторонней нагрузки), с `--duration 120`; (б) добавить сценарии потребителей Dramatiq
(orchestrator/exec на Fake CLI: run end-to-end в минуту) и 2+ диспетчеров outbox; (в) устранить потолок SSE
(§5.1) и повторить `--sse-clients 200 500`.
