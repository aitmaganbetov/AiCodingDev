# ADR-0016: Серверные персональные уведомления с отметкой прочтения

- **Статус:** Accepted (утверждено владельцем 2026-11-09: решение D-9 — «бэкенд-фазы B1–B8 одобрены»,
  `docs/planning/OPEN_QUESTIONS.md`, журнал решений)
- **Дата:** 2026-11-09
- **Связано:** UI_REDESIGN_PLAN §3.1, §3.10 G-15, §7.2 (фаза B8); ADR-0002 (outbox, идемпотентные потребители),
  ADR-0008 (tenancy/RLS), ADR-0011 (SSE из durable-журнала); API_DESIGN §13.1–13.2; DATABASE_DESIGN §9.10;
  EVENT_SCHEMAS §2.2, §3.2a; миграция 0020.

## Контекст

Колокольчик UI строился из потока workspace (`GET /workspaces/{id}/events`) и опроса approvals, а «прочитано» хранилось
курсором в `localStorage` устройства (G-15): история терялась при смене устройства, уведомления не были адресными
(весь поток workspace одинаков для всех участников), approvals без run (`DOCS_DOWNLOAD`, `VULN_DB_UPDATE`) в поток не
попадали. Нужна серверная история «кому и что» с отметкой прочтения — без новой инфраструктуры и без утечки
данных между пользователями.

ADR-0011 требует, чтобы UI-события run читались из durable `run_event_log` (порядок по `seq` в run). Уведомления —
другой класс данных: адресованы пользователю, не принадлежат run (часть — без run), имеют изменяемое состояние
(`read_at`). Класть их в `run_event_log` нельзя (журнал общий для всех участников и append-only).

## Решение

1. **Хранение — таблица `notifications`** (T, модуль `collaboration`, миграция 0020): строка = получатель × вид ×
   исходное outbox-событие; `UNIQUE (workspace_id, user_id, source_event_id, kind)`; составной FK на
   `workspace_members ON DELETE CASCADE`. RLS: `aicd_app` видит и меняет (только `read_at`) лишь строки
   `user_id = app_current_user()` текущего workspace; `aicd_worker` — вставка/чтение в workspace контекста;
   `aicd_maintenance` — retention 90 дней.
2. **Генерация — потребитель outbox** `notifications.project` (новая очередь Dramatiq `notifications`, обслуживает
   воркер orchestrator; worker-outbox ставит в неё события-источники в дополнение к обычной маршрутизации).
   Обработчик перечитывает состояние агрегата из PostgreSQL (payload — подсказка), определяет получателей по
   доменным правилам (кто может решить approval — та же функция `evaluate_decider`, что и API; инициатор решения;
   автор run/поручения) и пишет строки. Отметка `processed_events` и строки — в одной транзакции (at-least-once:
   сбой ⇒ откат ⇒ повтор); уникальный ключ — второй барьер. Набор видов минимален и перечислен в API_DESIGN §13.2;
   расширение — новое значение перечисления (CHECK + контракт).
3. **Содержимое без секретов:** шаблонный заголовок, редактированная выжимка (`redact_text`, ≤ 300 символов),
   идентификаторы для ссылок, ≤ 12 скаляров `data`. Payload доменных событий, вывод CLI и тексты агентов не
   копируются.
4. **Live-доставка — тот же поток workspace.** С каждой новой строкой в той же транзакции пишется outbox-событие
   `notification.created` (без проекции в `run_event_log`); после его публикации worker-outbox подаёт существующий
   сигнал `aicd:ws:{workspace_id}` (только пробуждение). Поток читает строки журнала run и уведомления **текущего
   пользователя** одним запросом (`UNION ALL`, RLS) в общем порядке `(created_at, event_id)` — курсор `id:`,
   перекрытие 60 с, окно повтора 24 ч и дедупликация клиентом по `event_id` те же, что в OQ-45 (c). Кадр —
   `SseNotificationCreated` (схема `notification-event.schema.json`, `seq = null`).
5. **API:** `GET /notifications` (keyset, `unread_only`, `kind`), `GET /notifications/unread-count`,
   `POST /notifications/mark-read` (по id, «до уведомления включительно», все; `Idempotency-Key`, аудит
   `notification.marked_read`). Права `notification:read` / `notification:update` — у всех ролей (видны только
   свои строки). Персональные настройки видов в v1 не реализованы.

## Альтернативы

- **Только клиент (`localStorage`, как раньше).** Нет истории между устройствами и адресности — отвергнуто (G-15).
- **Вычислять уведомления при чтении из `run_event_log`/approvals.** Дорогие запросы с правилами получателей на
  каждый запрос, нет устойчивого id для «прочитано», approvals без run не покрываются — отвергнуто.
- **Писать уведомления в транзакции доменного изменения** (в каждом сервисе). Размазывает правила получателей по
  модулям и удлиняет критичные транзакции (решение approval, переходы FSM) — отвергнуто в пользу одного потребителя.
- **Отдельный SSE-поток пользователя** (`/users/me/events`). Ещё одно соединение на вкладку (лимит 5 потоков на
  пользователя) и второй механизм курсора — отвергнуто: уведомления добавлены типом в существующий поток workspace.

## Последствия

- Новая очередь `notifications` (DLQ, метрики глубины, `GET /system/health`) и новый потребитель воркера
  orchestrator; без нового процесса и новых зависимостей.
- Задержка уведомления = outbox → Dramatiq → потребитель → outbox `notification.created` → сигнал (два цикла
  диспетчера, обычно < 2 с); потеря сигнала компенсируется опросом потока раз в 5 с.
- Уведомления — производные данные: downgrade миграции их удаляет, retention — через 90 дней; удаление участника
  удаляет его уведомления в workspace.
- `notification.created` — первый тип потока workspace не из `run_event_log`; клиенты, которые валидировали кадры
  только как `SseEnvelope`, должны учитывать `SseNotificationCreated` (`seq = null`).
