# ADR-0001: Modular Monolith + Workers

- **Статус:** Accepted (ТЗ §2 п.1, §22) — детализировано в Phase 0
- **Дата:** 2026-11-07

## Контекст
Платформа self-hosted, разворачивается одной командой/небольшой группой, должна работать локально (ТЗ §1). Нагрузочный профиль: десятки параллельных runs, ограниченные числом CLI-сессий подписок, а не CPU сервера. Требуются транзакционная согласованность FSM + outbox (ТЗ §16) и строгие границы модулей (ТЗ §17).

## Решение
1. Один Python-пакет (монорепозиторий `apps/` + `packages/`), один образ backend, несколько entrypoints: `api`, `worker-orchestrator`, `worker-outbox`, `worker-exec`, `worker-verify`, `worker-index`.
2. Модули (`packages/*`) общаются только через публичные сервисные интерфейсы (`<module>/api.py`) и доменные события; каждая таблица принадлежит ровно одному модулю (см. `MODULE_BOUNDARIES.md`).
3. Границы проверяются автоматически: `import-linter` контракты (layers + forbidden imports) в CI; запрещён доступ к ORM-моделям чужого модуля.
4. Воркеры масштабируются горизонтально числом процессов; `worker-exec` масштабируется по хостам с CLI.

## Альтернативы
- **Микросервисы** — отвергнуто: распределённые транзакции, сложность эксплуатации self-hosted, ТЗ запрещает преждевременное дробление.
- **Единый процесс без воркеров** — отвергнуто: CLI-исполнения длятся до 30+ мин, нарушили бы отзывчивость API и изоляцию.

## Последствия
+ Простая разработка, одна схема БД, атомарные транзакции.
− Нужна дисциплина границ (линтер), иначе «большой ком грязи».
− Обновление = перезапуск всех процессов; смягчается graceful shutdown + leases.

## Связанные требования
NFR-MAINT-01, NFR-MAINT-02, FR-ORCH-*, ТЗ §17.
